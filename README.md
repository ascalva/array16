# array16

[![ci](https://github.com/ascalva/array16/actions/workflows/ci.yml/badge.svg)](https://github.com/ascalva/array16/actions/workflows/ci.yml)

A phased-array software radio designed in code, and a theory-first investigation of a question about its fields:

> Can the fields an array generates form a closed shape that holds charged particles and accelerates them along
> it? And what do the particles' own fields add: can they be used to make that shape more exact?

The radio is a 4×4 array at 5.8 GHz with a redesign for 0.4-6 GHz. Its host library, simulator, controller
firmware and schematics are generated or tested from one description of the hardware. The investigation is run as
physics: the theory is written down first and its mathematics proved in Lean, a prediction and the criteria that
judge it are committed before the experiment that tests them, and every tool used or made here is open source.

## What has been found

- **What a radio-frequency field must be to hold a charge.** An oscillating field pushes a charge toward where
  the field is weak, into a well of depth `e²E²/(4mω²)`. For an electron that is 1 eV at 12 kV/m and 0.4 GHz, or
  at 73 kV/m and 2.45 GHz; halving the frequency deepens it fourfold. Elements a millimetre from the path reach
  those fields with tens of volts. So the array's geometry and frequency decide: where its elements sit around
  the path, and how slowly they may be driven (`experiments/accelerator/run.log`, closed forms).
- **A radio-frequency field alone guides electrons round a knot.** In the first run, four thin rods following a
  trefoil and driven at 1 GHz with 25 V between neighbours, a field whose null lies on the knot, held electrons
  of 0.5 to 8 eV for every lap tracked. The same shape at 60 Hz and ±500 V carries charged 10 µm glass grains
  round the knot in air (`experiments/accelerator/`; being redone on the new core).
- **Four phase-stepped gaps on one chirp accelerate.** Four gaps of 0.5 V round the loop, driven by one chirp
  from 58 to 113 MHz with 90° between neighbours, which is what four coherent radio channels supply, took a
  50 eV beam to 185 eV in 135 laps and captured 45 % of it (first run, a model of the motion along the path).
- **For a magnetic guide, the twist of the path holds an electron and its knot does not**
  (`experiments/guide_study.md`). Experiment 1 took the low-cost magnetic version of a closed guide, a winding
  on the path, with criteria committed before the run. A flat ring lost every electron at the predicted lap.
  A trefoil, a helix wound on a torus and a lifted figure-eight all held them, and the unknotted helix held four
  times the gyroradius the trefoil did. To first order one lap is the map `z ↦ exp(iα)·(z + ρG + H)` on the
  offset from the axis, where `α` is how far the path turns a frame carried round it; its laws are proved
  (`docs/LAWS.md`, GDE-1 to GDE-7).
- **Where the first-order theory stops.** It called held or lost correctly in 92 cases of 93 and the reach
  within 15 % in 54 of 55, and failed its registered test on the turn per lap, by up to 16.5°. Read after the
  run, most of that error is one term, ρ × (the path's bending) / 2, matching to 2 % with nothing fitted: the next
  hypothesis (GDE-H2).
- **A knot costs bending.** A knotted curve's total curvature exceeds 4π, so its bending exceeds 16π² over its
  length, four times a circle's (CUR-2, proved from the cited theorem).

## Run it

    uv sync --extra dev                  # the environment, from uv.lock
    uv run pytest                        # 150 tests, about 12 s
    uv run ruff check && uv run mypy     # lint and strict types, for the files named in pyproject.toml
    (cd formal && lake exe cache get) && ./formal/check.sh    # the proofs; needs elan, and about 7 GB for Mathlib

Twenty of the tests run the firmware in an emulator, given `node`, rp2040js and a built firmware image
(`firmware/README.md`, `firmware/emu/README.md`); the firmware-core tests use the local C compiler.

A first session with the simulated board:

    from array16 import Array
    from array16.sim import SimBackend, Source

    sim = SimBackend("quad")                  # four coherent channels; "hackrf" for one HackRF alone
    arr = Array(sim)
    sim.sources = [Source(0, 0, -75)]         # a test source straight ahead
    arr.calibrate()
    sim.sources = [Source(25, 30, -75, kind="qpsk")]
    print(arr.locate(blind=True))             # about (25, 30) degrees

An experiment on the harness has three steps, and the second starts once the first is committed:

    uv run python experiments/guide_study.py predict     # the theory's predictions, for every shot
    uv run python experiments/guide_study.py run         # the measurements not yet on file; --bench NAME
    uv run python experiments/guide_study.py report      # the verdicts, by criteria fixed beforehand

The older studies are scripts that write their results beside them:

    uv run python experiments/virtual_bringup.py     # statistics over 40 simulated boards
    uv run python experiments/antenna_study.py       # patches, coupling, scanning, direction finding (about 75 s)
    uv run python experiments/accelerator_study.py   # the first particle run (about 3 min)

`hw/design.py` regenerates the KiCad project with KiCad 7 or later. `experiments/vivaldi_openems.py` runs on
openEMS with its Python modules (`experiments/vivaldi/README.md`).

## How the work is done

1. **Theory first.** A question is worked on paper before anything is tracked: what the fields are, what they do
   to a charge, what numbers decide the outcome. The mathematics the code relies on is proved in Lean
   (`formal/`), over a model of the code in exact arithmetic, and property tests attack the floating-point
   implementation of the same laws.
2. **Calibrate the instrument.** The integrator, the curves and the windings are tested against results known in
   closed form before any experiment uses them: gyration, the E×B drift and its step error, Mathieu's stability
   boundary, Ampère's law round a winding, writhe against holonomy.
3. **Predict, then run.** The prediction, and what would count as its failure, are committed before the run that
   tests them. `array16.lab` enforces it: it measures once the predictions are committed, and stores with every
   measurement the commit, the bench and the versions that made it. What is found by looking at the results
   afterwards is kept apart and called a hypothesis.
4. **Keep a case that must fail.** A ring beside every knot, a false statement beside every law. A check is
   trusted once it has been seen to fail.
5. **Label every claim.** `docs/LAWS.md` gives each law one row: its statement, the code that relies on it, a
   label, the test that would catch it false and the Lean declarations that state it. A *Proposition* is proved,
   a *Claim* is supported by a named test, a *Hypothesis* is a physical model that experiments support or
   falsify. `tests/test_laws.py` checks the ledger against the code in both directions.
6. **State the model.** Point charges, thin-wire electrodes, filament windings, one particle at a time: each
   report says what its numbers were computed with.
7. **One experiment, any bench.** An experiment asks for what it needs by role, a radio or a positioner or only
   processes, and a bench file says what plays each role (`benches/README.md`). Moving from a simulator to the
   hardware is a change of bench and not of experiment.
8. **Open source throughout.** uv, ruff, mypy, pytest and Hypothesis, NumPy, Lean and Mathlib, KiCad, openEMS;
   and what is built here is public under the license below.

New Python is typed (`mypy --strict`), linted and formatted (`ruff`) and tested, and runs through `uv`. The files
held to that are named in `pyproject.toml`; the older ones join the list as they are brought up to it.

## Layout

| Path | What it is |
| --- | --- |
| `array16/board.py` | Geometry, RF budget and the 56-bit control word: the single description of the hardware |
| `array16/control.py`, `dsp.py`, `api.py` | Beam states and snapshot schedules; alignment, decoding and direction finding; `Array`, the object a user holds |
| `array16/sim.py`, `antenna.py`, `fwsim.py` | The simulated board, scene and radios; coupled patches; the controller's reference model |
| `array16/evolve.py` | Search by small changes that keep what works |
| `array16/particles/` | Charged particles in prescribed fields: the Boris step, one loop for every tracker, closed curves, rods and windings, the first-order theory of a guide field |
| `array16/lab.py` | The experiment harness: predict, run, report; benches; provenance |
| `benches/` | Resource setups: compute, and devices by role |
| `tests/` | The virtual bench, the firmware against its model, the particle core against closed forms, the harness on a toy experiment, the ledger against the code |
| `firmware/` | The RP2040 beam controller: a portable core, and PIO, DMA, clocks and USB around it |
| `hw/` | The circuit as a script (`design.py`), the KiCad project it generates, and the 26 schematic pages |
| `experiments/` | The studies and experiments: each a script, its outputs and a written report |
| `docs/LAWS.md` | The laws ledger |
| `docs/PROGRESS.md` | Where the work stands, and what is next |
| `formal/` | The Lean proofs behind the ledger, and their gate, `check.sh` |
| `ARCHITECTURE.md` | How the radio's pieces fit, the controller protocol, calibration, open issues |
| `REDESIGN.md` | The 0.4-6 GHz proposal |
| `AGENTS.md` | Orientation for an agent working in this repository |
